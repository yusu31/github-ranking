# テスト設計: github-ranking

## 1. 方針
- ケースは思いつきで選ばず、下の技法で決める。「止めてはいけないもの（通すもの）」も同じ数だけ入れる
- 新しいテストは、実装前に一度落ちる（赤）ことを確認してから緑にする
- 完了＝テストの**実行件数が表示された**こと
- 本物のデータ・設定には触れず、一時フォルダと合成入力で試す

## 2. ケースの決め方
| 技法 | 使いどころ | 例 |
|---|---|---|
| 同値分割 | 入力を「同じ扱いになるグループ」に分け、各グループから1つ選ぶ | 0 未満／0〜100／101 以上 |
| 境界値分析 | グループの切り替わり目を狙う（バグはここに出る） | -1・0・100・101 |
| デシジョンテーブル | 条件の組み合わせごとの結果を表にして漏れなく試す | 条件A×条件B の4通り |
| 呼ばれないこと | 弾かれたとき、その先の処理（保存・外部通信）が**実行されていない**ことを確かめる | 不正入力で保存が0回 |

## 3. カバレッジに数値の基準を設けない理由
「80% 以上」のような数値を基準にすると、数値を満たすためだけの**中身のないテスト**（何も検証せず行を通すだけ）が増える。通った行の割合は、バグを見つける力を測っていない。
代わりに次を必須にする。
1. **実行件数の表示**（0件で緑になるのを防ぐ）
2. **赤の確認**（落ちるべき変更を作り、テストが本当に落ちる所を見る）
カバレッジは「テストが届いていない場所を探す参考」として見るのはよい。合否の基準にはしない。
