- **ID**: `W-01` のように、作業ごとに一意な番号。
- **フェーズ**: [requirements.md](requirements.md) の §11 の Phase の番号をそのまま使います（名前は書かない。二重に持たないため）。
- **領域**（大分類）: その作業の分野。下の8語から選びます。**空でもよい**。空なら、ダッシュボードが PR の変更ファイルから推定します（「推定」と表示）。
- **中分類**（任意）: このプロジェクト独自の細かい分け方（例: CLI・認証・決済）。空でもよい。
- **作業**: 何をやるか。短く。
- **内容**（任意）: 何をするのかの説明。初めて読む人が分かる細かさで。空でもよい。
- **Issue**: `#12` のように書く。まだ起票していなければ**空**（ダッシュボードは「未起票」と表示します）。起票したらここに番号を足します。
- **種類**（小分類）: 下の表の語から選びます。
- **見積もり**（任意）: 通しで作業した場合の時間の目安。`30分`・`2h`・`1.5h` の形（日は使わない）。空なら時間は出ません。
- 表に **中分類・内容・見積もり** の列が無い roadmap でも動きます（無い列は空として扱います）。

## 領域（大分類）

領域は、次の8語から選びます（プロジェクトの分野の共通の分け方）: **フロントエンド・バックエンド・データベース・インフラ・デプロイ・CI・テスト・文書・開発の仕組み**。
CLI・認証など、このプロジェクト独自の細かい分け方は「中分類」に書きます。

## 種類（小分類）

作業の「種類」から、ダッシュボードが作業に向くモデルと思考レベルの**目安**を出します（測った値ではありません）。

| 種類 | 使う場面 |
|---|---|
| 計画 | 順番と範囲を決める |
| 要件 | 何を作るかを決める |
| 調査 | 調べて比べる（ライブラリ・方式・不具合の原因）。下調べは Haiku のサブエージェント、裏取りはメイン |
| 設計 | どう作るかを決める。比較して、却下案と理由も残す |
| 実装 | 新しい機能を作る |
| 修正 | 不具合を直す（詰まったら Opus） |
| 整備 | 環境構築・設定・リファクタ |
| テスト | 動作を確かめる仕組みを作る |
| レビュー | できたものを壊す側の目で確かめる |
| 文書 | 説明・手順・記録を書く |
| 公開 | 外に出す・お金がかかる操作（本人の確認が要る） |
| 運用 | 観察・障害対応・棚卸し |
