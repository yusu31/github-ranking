## 1. 概要
### 目的
GitHub の流行と、自分の関心領域の新しい道具を**毎朝素早くつかみ、自分と開発環境を高める**（情報収集が主）。公開して、作品としても「自分の課題を自分で自動化した」と語れる形にする。

### 背景
- 本人の言葉（2026-11-10）: 「関心領域はもちろんだが、Trending も追っかけていきたい。なるべく流行りや最新情報は素早くキャッチし、自分や環境を高めていきたい」
- 2026-10-26 の別プロジェクトの調査で、GitHub Trending の上位は AI エージェント系が多く、自分の領域の道具は埋もれていた。**全体の上位と、関心領域の上位の両方**が要る
- 全体のランキングは既存サービス（trendshift.io・OSS Insight・star-history）がある。このプロダクトの差は「自分の関心領域に絞る」「日本語の1行要約」「毎朝 Obsidian にたまる」
- GitHub Actions の定期実行で回すので、Claude Code の使用量を使わない

### 作るもの（Phase 1 で AC を付ける）
| 区分 | 機能 |
|---|---|
| 必須 | ① GitHub Trending の毎日の記録 ② 関心領域（例: shadcn・GSAP・Three.js・Phaser・Claude Code のスキルと MCP）の★急上昇 ③ GitHub Models の無料枠による日本語の1行要約 ④ 取り始めた日からの★の履歴 ⑤ 毎朝の日報を Obsidian 向け Markdown で書き出す（手元の Vault への取り込み方法は Phase 3 で比較し本人が決める） |
| できれば | ⑥ お気に入り（ブラウザに保存・ログインなし）⑦ お気に入りを週1回まとめて Obsidian に送る（`obsidian://` リンク。Vault 名はコードに書かず画面の設定で入れる） |
| 作らない | 通知（メール・LINE・Slack）／ログイン／過去の★の遡り（star-history へのリンクで補う）／1件ずつ Obsidian に送るボタン（毎回選ぶのが面倒と本人指摘） |

削る順（時間が足りないとき）: ⑦ → ⑥ → ③（要約なしでも英語の説明で成り立つ）

## 2. 前提条件・制約
- **お金をかけない**: GitHub Actions・Pages は公開リポジトリの無料の範囲。GitHub Models は無料枠だけ使い、**超過分の支払いは有効にしない**。無料枠を超えた日は要約を飛ばして英語の説明を出す
- **頻度**: 毎朝1回（日本時間）
- **GitHub のルールを守る**（本人の条件「規則違反や、なにかのルールを犯すのは無し」）:
  - Trending ページ（公式 API が無く HTML だけ）は、`robots.txt` で全ロボットに許可されている（2026-11-10 確認）。規約（Acceptable Use Policies §7）が認める**記録保存（archival）**の使い方にする
  - 読むのは1日1回・数ページだけ。取得元に名乗る（User-Agent にリポジトリ名）。公開情報（リポジトリ名・説明・言語・★）だけを取り、作者のメール等の個人情報は取らない。出典を明記し、集めたデータも公開する
  - 公式の API で取れるものは API で取る（規約上 API は scraping に当たらない）
  - `robots.txt` か規約が変わって許可が外れたら、Trending の取得を止める。Trending が読めない日は、公式 API の「直近に作られた★急上昇」で代わりに出す
- 大きさ M（ログイン・DB・課金なし）。これらが要るようになったら `rt recommend` で測り直す

## 3. 対象ユーザー
- 主: 本人（毎朝ページか Obsidian の日報を見る）
- 副: 公開ページを見る人（同じ領域の開発者・採用側）。ログインなしで読める

## 5. 非機能要件
「どれくらいの品質で動くか」を、確かめられる数値で書く。
- **目標値は余裕を持たせる**: 限界ぎりぎりを目標にしない（少し遅くなっただけで要件を割るため）。上限の値と、内部の目標（それより厳しい値）を分けてもよい
- **根拠**: 公的な指標・調査・実測など、数値の出どころを書く。推測なら「推測」と書き、測ったら直す
- **測り方**: 道具・条件（端末・回線・データ量）・どの値を見るか。測り方が書けない項目は要件にしない

## 10. リスクと対策
| # | リスク | 対策 |
|---|---|---|
| R-01 | 公開リポジトリの定期実行は、60日間リポジトリに動きが無いと自動で止まる（GitHub Docs） | 毎朝のデータ記録のコミットで防げるかを Phase 3 で確かめる。止まったときの気付き方と戻し方を runbook に書く |
| R-02 | Trending の HTML が変わると読み取りが壊れる | 壊れても処理全体は止めず、API の代わりのデータで出す。壊れた日を記録して気付けるようにする |
| R-03 | GitHub Models の無料枠の回数が足りない・変わる | 無料枠の数値は Phase 3 で API（`/catalog/models`）を実際に読んで決める。超えた日は要約を飛ばす |
| R-04 | 規約・robots.txt が変わり、Trending の取得が許可されなくなる | 取得前に確かめる手順を runbook に置き、外れたら止める |
| R-05 | 作って満足し、見なくなる | 日報が Obsidian に自動でたまる形にする。Phase 10 で「週に何回開いたか」で判定する |

## 11. フェーズ
大きさ **M**（数週間・公開するがログインや課金は無い）。プロトタイプで要件を確かめ、設計は軽めにする。公開までの経路は土台で1回通す（独立した技術スパイクは置かない）。ログイン・課金・DB つきの公開が必要になったら、`rt recommend` で測り直す。

| Phase | 内容 | 成果物 | 完了条件 | 本人確認 |
|---|---|---|---|---|
| 0 | 合意 | 目的・範囲・作らないもの・大きさ（M）の合意 | 本人が承認 | 計画の承認 |
| 1 | 要件のたたき台 | requirements.md（必須／できれば／やらない・削る順）と features.md の AC | 必須の機能に AC がある | たたき台の承認 |
| 2 | プロトタイプ | prototype/（使い捨て。画面の流れを静的 HTML などで見る。要件を確かめる道具） | 見て直した点を requirements.md に反映した | 見た目と流れの承認 |
| 3 | 基本設計（軽め） | profile の設計文書と docs/adr/。決めたことだけ書く | 要件と矛盾しない | 設計の承認 |
| 4 | 開発の準備 | CI・Issue/PR テンプレ・作業ルール・docs/schedule.md（順番・見積もり・確かめる日） | 空のテストが CI で緑（実行件数が出る） | 日程の承認 |
| 5 | 土台 | 骨組みと、公開までの経路を1回通す | 最小の画面（または出力）が公開先で見える | なし |
| 6 | 実装 | 必須 → できれば（削る順に従う）。各 PR でプロトタイプと見比べる | 必須の AC をすべて満たす（テストの実行件数） | 機能ごと |
| 7 | 品質チェック | lint・テスト・ビルド・反証型 QA・E2E（画面がある場合） | 全部合格 | なし |
| 8 | 納品レビュー | docs/delivery.md（AC の対照表・デモ動画・本人が触る手順・既知の不具合と見送り・リリースノート・判定） | 本人が動画と手順で確かめ、判定を日付つきで書いた。直す点は Issue にした | 判定（OK／直す点） |
| 9 | 公開 | 公開・README・docs/runbook.md（困ったときと戻し方） | 公開先で主要な流れが動く | 公開の承認（対外的な発信） |
| 10 | 判定・記録 | 結果の判定、採用案と却下案の記録 | 証拠つきの判定 | 判定の承認 |
